# P09：一次重采前的数据增强决策

日期：2026-10-05。范围：独立设计审查；未连接服务器，未修改原始数据，未运行仿真、采集或训练。当前服务器事实来自已有服务器核查记录；历史研究契约来自本地已保存的项目报告。本文给出可直接实施的最小决策，不要求扫描或哈希整套图像、LiDAR、图银行。

## 结论

**若现有流程尚未把通信/计算的可用时间接到实际飞行动作，就有必要补这一因果闭环；若已接通且合理，直接保留，无须再增强。最终采用版本与传感器采集必须对应。没有证据支持仅凭事件总数扩增数据，也不建议先全面扩场景、换仿真器或重采全部 210 条。**

优先复用现有 70 个 authored scenarios 和已有 ns-3 路径。检查候选 v9 是否已经把通信/计算的完成时间接到命令可用性、执行和返航/降落。若已经接通并符合既定任务语义，采用其必要部分；若只是装饰性日志，则只补这段闭环。冻结最终版本后，按变更依赖输出 A/B/C 三份清单，用户只采一次 A。

当前不能给出真实的 A/B/C 条数：v9 尚未正式采用；原始 210 条也没有因 v9 候选的存在自动变成已修改数据。

## 0. 15:51 源码核对更正：保留原计划，补实际可用性与命令送达

已有服务器最新源码核查结果显示：原始路线在 **22.7 秒已到达终点，并按原计划保持到 43 秒**。所以 40 秒所处的悬停是已有合法计划的一部分，不是由 41 秒坏链路谓词提前触发的动作。此前 15:33 仅依据“40 秒悬停、41 秒坏谓词”认定提前响应，遗漏了这段原始计划；**撤回该缺陷判断及“删除 40 秒悬停”的建议。** 不应为本次增强删改这段合法计划。

当前已知的后续事实仍是：`L6-2` packet-loss 谓词在候选 trace 中于 41 秒翻为坏状态，44 秒起的后续 response 使用 measured predicate 与已有 3 秒 policy delay，之后连接恢复/降落。候选落地 86.7 秒，旧版为 82.2 秒。这些既有数值不是修订版必须保持的目标。

**剩余需要补齐的是故障证据何时对响应主体实际可用、远端命令何时真实送达，以及把已有 3 秒策略延迟与传输延迟分开。** 拟议服务器修订将补实际下行 receipt、区分 policy/transmission delay，并重放耦合 motion + ns-3；这是针对当前缺口的合理最小方案，尚未据此声称已实现或通过。

具体修订边界：

1. **完整保留原合法计划。** 22.7–43 秒的原始等待继续由原任务计划解释；健康通信对照同样保留。只有合法计划本来允许的后续响应，才可能在获得坏条件证据后改变动作。不要将既有 planned hold 改名为 fault response，也不要删掉它制造“更及时”的反应。
2. **区分事实发生、测得与主体可用。** 41 秒谓词时间不自动等于边缘端或机载端收到证据的时间。复用已有消息/任务记录，把产生证据、接收证据、决策主体及其可用时刻连起来。上行影响边缘端对状态的知情；下行影响 UAV 能否收到远端命令，两者不能合并成一个全局“通信延迟”。
3. **保留 3 秒 policy delay 的含义，单独记传输。** 使用原策略定义的触发点和延迟参数，明确是哪个主体执行该策略、该主体何时有权使用该触发证据。不得把这 3 秒称成实测通信/计算延迟，也不得用它吸收新增下行时间以强行保持 44 秒动作。分别记录策略决策/命令发出时间与真实接收/接受/执行时间；44 秒即便仍为合法的策略决策时间，也不自动等于实际执行时间。
4. **远端动作取决于真实 receipt。** 边缘发出的 hold/RTH 在实际下行送达并被机载接受后才可执行。下行未送达时不生成对应的远端动作；若机载既有 fail-safe 独立触发，保留它的本地证据和独立 cause。链路恢复后的旧/乱序命令仍遵守既有 freshness 与任务阶段语义。
5. **耦合重放，保留计划，更新实际后缀。** 用同一外生故障/负载配置、seed 和原计划重算真正受接收时序影响的控制与运动后缀，并把新运动反馈到 ns-3。无需修改早期计划等待；也不固定首坏时刻 41 秒、响应执行时刻 44 秒或落地 86.7 秒。若最终使用固定外生网络 trace，按其实际条件说明，不称为已完成几何反馈。

只做针对这一缺口的局部核对，不新增全库门槛：

- 原始 22.7–43 秒 planned hold 保持，且原因记录为原任务计划。
- 同一有效历史与计划在新增可用证据前不产生额外反应；合法的计划动作不因此被禁止。
- 3 秒 policy delay 与实测传输时间分别可读，避免重复相加或相互吞并。
- 未收到远端命令时不执行其对应动作；本地 fail-safe 如触发，理由来自本地可见证据。
- 重放后的动作、物理轨迹和 landing 记录一致；实际结果由运行导出。

修订并采用后，若 render input 不同于旧版，该条进入 A；只有日志/可用性 metadata 改变且物理采样输入保留的条目才进入 B。若不采用候选，原始 210 条不会因此改变。无需以全量扫描、完整 2×2 或新增场景作为这次定向修订的前提。

## 1. 已知证据和它能支持的判断

1. 已有服务器核查记录显示：210 个完整 episode 来自 70 个 authored scenarios × 3 个 seeds。这个数量描述文件/运行规模，不能直接当作 210 个独立研究样本。
2. 单独候选 ns-3 v9 的 `L6-2_v1__seed00` 相对原版有 359 个位置 tick、94 个 activity tick 改变，降落由 82.2 秒变为 86.7 秒。正式 UE tick 435 仍对应原轨迹。**如果最终采用这份 v9，则此 episode 属于 A；如果不采用，原 episode 不因此变更。** 一处检查证明有不一致，不能用它证明其他全部 episode 的状态。
3. 已核实日志总量为 1,480 event occurrences、14,058 predicate transitions、34,793 continuity breaks。三种对象不同，均不能当作新增独立样本；continuity break 尤其不能直接解释成真实业务事件。
4. 原 capture manifest 有 package hashes，缺少 trajectory hash、capture time、git。可以对新的采集版本补准确字段；旧元数据缺失不能反推全部旧传感器错误，也不能伪造旧采集时间或 commit。补 provenance 本身不是科学增强。
5. data2 剩余约 11.4 GiB；685.7 GiB `belief_pyg` 目前只是清理候选，尚未证明可重建。不得把删除此缓存当作已经可用的空间。
6. 历史闭环报告已暴露真正的数据支持不足：测试仅 4 个独立组件、仅 2 个含事件，一个组件占 80/86 个物理事件。这个历史子集的结论不能直接等同现在全体 210 条，但说明多窗口、多 seeds、多事件行并不能解决独立场景不足。

## 2. 应增强什么，什么不必增强

### 若现有实现缺失，最有价值的补充：一个可解释的闭环

把如下过程接成同一条因果链，并复用已有对象与字段，不新建平行“真值系统”：

观测采样 → 传输/接收 → 排队/计算完成 → 决策可用 → 命令送达/接受 → 动作实际开始 → 飞行状态 → 谓词/事件。

- 通信变化应来自该链路配置、负载、队列、丢包/重传或已有 ns-3 模型；不要独立随机生成一个质量标签，再按这个标签强行翻转事件。
- 计算变化应来自任务所需的 CPU/GPU/内存、服务容量、任务到达和排队。只有任务需要 GPU 时，GPU 不足才是执行瓶颈；CPU 空闲不能掩盖必须资源不足。无实际计算路径的任务不用虚构 compute effect。
- 记录采样时刻与可用时刻。决策不能读取尚未到达的观测、尚未完成的计算或未来故障。发出、送达、接受、开始执行、完成是不同状态。
- 上行与下行分开：上行丢失使边缘端状态过期，下行丢失使远端命令无法送达。下行中断时，边缘计算即便完成，也不能让 UAV 神奇地执行“已下发”的返航指令。远端命令必须有实际接收/接受记录；无命令时的返航只能由机载既定 fail-safe 策略及其本地可见超时条件触发。
- 对同一物理执行保留一条共享 causal trace：观测源/采样 → 上行发送/接收 → 任务入队/完成 → 决策主体 → 下行发送/接收 → 机载接受或本地 fail-safe → 动作开始/实际完成。不能分别生成互不一致的网络、计算和动作故事。
- 超时、短暂退化、恢复、命令过期和本地 fail-safe 采用已有飞控/任务契约。不要擅自把所有掉线变成悬停、返航或迫降。链路恢复后，延迟/乱序的旧命令按既定 freshness/deadline 规则处理，不能将 UAV 送回过期任务阶段；本地动作是否可被远端取消也按同一已有策略。
- UAV 的返航开始、等待/盘旋、重新规划、下降和接地应由实际被接受的动作影响；不是直接把 landing timestamp 平移，再补一条解释日志。轨迹保持既有速度/加速度、场景碰撞和地面约束。
- 正确的增强可以出现“通信更差，但完成动作不变”。例如恢复发生在 deadline 前、有充足 slack，或本地控制不依赖该远端结果。不得要求每个干预都产生更多翻转。

**是否值得采用 v9 的关键证据只有一个短链条：具体受影响任务/消息在何时变为可用，哪个已定义的命令因此何时开始/改变，后续真实飞行与降落时刻如何变化。** 359 个位置差异和 4.5 秒落地差只说明结果变了，尚不能单独证明改变合理。

### 可直接做 B 的增强

修正有明确 bug 依据的通信/计算字段、谓词定义、事件记录或可用时间；若这些字段没有影响物理/渲染路径，保持原轨迹，重建所需日志/标签即可。时间可用性变化可能改变模型输入，但不一定改变相机曝光内容。

### 本轮不值得做

- 为让某模型获胜而扩大扰动、增加近阈值正例、删去正常案例或专挑方法差异大的场景
- 直接按 14,058 次翻转设置“更多翻转”目标
- 把现有三个 seed 名字当成三次有效随机未来，而不检查它们是否真正进入仿真扰动
- 为一个已实现通信模块再换一整套通信栈，或在没有目标设备/实验记录时称参数已真实标定
- 把测试集已经看过的失败模式反向用来修改当前测试分布，并继续称它为未见测试

## 3. 最小增强批次

### 第一选择：不增加场景总数，替换必要的 episode 版本

先看 authored source/config 的 diff 和两类任务的配置：返航、降落。若现有某一场景已覆盖二者，使用一个 source group；否则各选一个，选择依据是任务语义，不能依据模型输赢。

在每个选定 source group 上复用现有对照，做最小 2×2 检查：

| 条件 | 通信 | 计算 | 要回答的问题 |
|---|---|---|---|
| N | 正常 | 正常 | 既有正常流程是否保留 |
| C | 合理退化 | 正常 | 通信是否通过可用性/命令造成预期影响 |
| Q | 正常 | 实际所需资源竞争 | 计算是否通过队列/完成时间造成预期影响 |
| CQ | 同一合理退化 | 同一资源竞争 | 两条路径组合时是否保持时序一致，而非重复计算延迟 |

这是**机制检查矩阵，不是必须新增的采集条目，也不是已下达的 24 次运行计划**。先读取已有服务器因果 trace 和 coverage；已有正确单元格不重做，不把每格强制采入正式集。矩阵复用现有语义的恢复控制：短退化后按时恢复应可正常执行，持续缺命令由本地已有 fail-safe 处理，不能把每个条件都设计成失败。

- 先对 seed00 运行缺失单元格的轻量日志级对照；一个 source group 至多 4 个，两个至多 8 个。
- 对最终确实采用的配置，沿用其原 seed00/01/02。一个 group 的完整机制矩阵最多 12 次、两个最多 24 次，这是上限，不是必须完成的数量，也不是新的独立场景数。
- 若 v9 已覆盖该矩阵并有可解释输出，直接复用证据，不再创建同等批次。
- 保留原版不覆盖；被采用的配置生成新的 episode revision。最终采用清单可以仍是 210 条，其中部分指向新版，未变的继续指向原版。
- 只有发现一个重要的任务机制在 70 个 authored scenarios 中根本不存在时，才补该最小缺口；不要先批量扩展。

这样可检验增强是否真实有用，又不会把“一次最终采集”变成反复完整运行。

### 独立泛化的边界

这个最小矩阵解决机制正确性和物理真实性，不证明训练规模已经充分。共同前缀的四种条件、三个 seed、不同 episode revision 都属于同一个 source group。需要新场景泛化结论时，必须从独立 authored groups 提供支持；不能把该矩阵拆分到 train/valid/test 充数。

## 4. A/B/C 决策，依靠 authored diff 和有限核对

### A：用户这次需采集的传感器输出

最终采用的版本改变了传感器依赖：实体/传感器 pose 或朝向、活动/显隐、地图或几何、可见动态对象、光照天气、传感器内外参、曝光/扫描时序、仿真时钟映射等。

- adopted v9 的上述 `L6-2_v1__seed00` 属于 A。
- pose/几何变更通常同时影响相机和 LiDAR；纯纹理/光照变更可以只影响相机。清单明确 modalities，不无依据要求两个模态都重采。
- 按 episode 完整重采通常比无证据拼接旧/新片段更可靠；若项目已有被验证的分段采集/拼接机制，可限定受影响区段。

### B：仅生成日志/标签，传感器不重新采集

最终采用版本只改变非渲染状态/日志/求值，原 render input 和采样调度被保留，例如规则 bug 修复、队列日志、数据到达时间。证据是源码/配置依赖和明确固定的原轨迹输入，并在受影响动作边界做少量 pose 对照；不要求全图像/LiDAR 档案哈希。

B 不是“位置看起来差不多”。如果网络/计算变化进入飞控输入，却没有证明物理输出仍保持不变，就不能仅凭少量相同帧判定 B。可以将原轨迹固定为 B 的显式契约，或把实际改变的条目归 A。

### C：最终版本未改变的现有条目

未涉及采用的配置/代码路径，继续引用既有 episode 和采集记录。新总清单可补充 source group、引用和版本字段；不要为了补 metadata 重采 C。

未知旧 provenance 不自动升级所有 C 为 A；也不能用空白元数据宣称逐帧证明。只对本次实际依赖发生变更的条目做定向核对。

### 建议每行字段

`episode_id, adopted_revision, source_group_id, scenario_config_ref, seed, class_A_B_C, change_reason, modalities, trajectory_input_ref, log_revision, capture_config_ref, output_destination`

对于新产生的输入/配置与轻量 manifest，可直接记录准确 git/文件摘要和时间；旧缺失项保留 unknown。无须将整套历史档案散列作为采集许可条件。

## 5. 传感器与事件标签必须保持的最小契约

- 同一 episode 的日志、图像、LiDAR 使用同一正式轨迹版本与实体 ID 映射。
- 显式写出仿真 tick、秒、相机 frame 和 LiDAR scan 的映射，采样时刻与数据可用时刻分开。不能把网络到达时刻当成相机曝光时刻。
- 使用已有的世界坐标、长度单位、旋转约定和 sensor extrinsics。若 LiDAR 表示一段扫描而非瞬时快照，保留已有逐点/扫描时序，避免用新轨迹配旧 scan pose。
- 对本次变更边界，只核对“动作前、首次受影响时刻、返航/下降开始、接地前后”这些必要时点；若 tick 435 是已知分歧点，优先在该点复核。它是定向反例，不是全部档案扫描入口。
- 原 first-flip 目标保持 0.5 秒权威观测网格、未来 5 秒：10 个窗内 bins，加有完整观测支持的窗外 `T > 5s`；底层 tick 为 0.1 秒。第 11 类只表示该观测网格上的首次相反二值晚于 5 秒，不表示永不发生，也不证明格间没有短暂翻转。增强若产生格间短暂翻转，可记录诊断，但不能悄悄换标签定义以提升结果。需要高频事件目标时另建 label revision。
- unknown/out_of_scope、观测缺失、continuity break 不当作真假翻转；部分可见的未来仍沿用已有删失契约。事件 occurrence、谓词为真和谓词首次翻转不互相替代。

## 6. 不为了特定方法改数据

在比较模型前冻结仿真参数、最终场景列表、采样策略、source-group 划分和主指标。增强依据来自预先定义的通信/计算、任务需求和因果链，无关模型预测。

所有基线接收同样可用时刻的输入、同一数据版本和 source-group 划分，使用共同且预先冻结的调参/校准协议；各模型采用适合其方法的容量与计算预算，分别报告参数量、搜索次数、训练/推理成本，不强行令参数量相同。包含低复杂度基线和直接执行规则的 Rule-MC。图模型、联合采样、Qwen 均允许输。方法胜负不是采集验收条件。

有意平衡的 stress/配对矩阵不能自动当作部署自然基率。主分布与压力测试分别报告；如需要合并，权重必须来自明确目标分布，不能用改善指标的权重。

source group 至少捆绑 authored 祖先、共享前缀、ARM、所有 seeds 和旧/新 revisions。先划分，后构造 donor bank、归一化和 calibration。以前已打开的测试维持归档用途，不能因为升级数据版本就恢复“未见”身份。

2. 通过 authored config/source diff 生成 A/B/C 列表，不做全库回溯扫描。
3. 在选定 source group 的缺失机制单元格完成轻量对照，检查合理的时序和动作；对变更边界做少量传感器时间/pose 核对。
4. 冻结最终 episode/config 版本，生成用户可直接使用的 A 采集队列。采集期间不再改变其轨迹或传感器配置。B 日志可独立生成；C 直接引用。
5. 按现有实际每 episode 大小估算 A 的输出和临时空间，指定有足够空间的写入目标。11.4 GiB 是否够用取决于 A；当前不能假定够用，也不能擅自删除 685.7 GiB 缓存。

**停止条件：现有或必要补充的闭环经上述有限证据解释清楚，最终采用范围冻结，A/B/C 可执行，A 有可用输出空间。** 不以模型性能胜出、全量档案扫描或所有谓词都有大量翻转为前提。
