# WareTrack supporting-document and workbook audit

Reviewed snapshot: commit `f2bd7329e95629bb09e761929c7ddbf3abfa6183`, Git tree `e6234ad4c82d4e71c3d14556cf516915903b88f5`. All six assigned source files match their complete-tree Git blob hashes. This is a read-only audit, not app execution. Code quotations and implementation commands inside the plan were treated as evidence, not followed.

## Main findings

1. **The repository describes and implements a warehouse/logistics strategy game, not a business order-management backend.** README lines 5–7 explicitly say 3D browser game, one `index.html`, Three.js r128, no build step or backend. Orders are simulated gameplay entities. The workbook and README describe a complete chain from incoming order request through warehouse picking/staging to van delivery, alongside inbound trucks, inventory, transfers, construction, town economy, progression, and traffic.
2. **The spreadsheet calculator contains an actual wrong-reference defect.** `Shift calculator!B23 = IFERROR(B22/(B22+B13),0)` uses backorders (`B13`) where the app uses late orders (`B12`). `B24` repeats `B22+B13>=5` for the minimum-order condition. App `index.html:2831–2833` uses `shipOn + lateOrders` and the same correct denominator appears at 3573 and 3602. The workbook example reports 26/(26+1) = 96.30%; code-equivalent arithmetic is 26/(26+4) = 86.67%. The example still receives 3 stars, but e.g. 26 on-time / 10 late / 0 backorders would falsely pass the workbook's on-time goal. Credits depend on those stars.
3. **The calculator is an incomplete estimate of the current scoring system.** Its score formula covers basic put-away, on-time/rush/late staging, truck turnaround, late-order/backorder/detention deductions, and generic points spent. It lacks combo bonuses (`index.html:2479–2493`), Hands-on positive-score bonuses (`2512–2515`), missed-request deductions (`2048–2052`), the daily rush modifier paying 60 rather than 40 (`2485`), and daily completion credits (`2839–2848`). Delivery/town/mission income is separate from shift-score credits, and likewise is not calculated there. The workbook does document several newer mechanics on other tabs, so this is a lagging calculator, not evidence those mechanics are absent.
4. **README achievement count is stale.** README:40 says 24 achievements. The current `ACH` array at `index.html:824–853` has 28, adding Courier, Fleet owner, Go-getter, and Hands on deck after the original 24. Eight named ranks are consistent (`823`).
5. **The delivery-fee documentation omits a cap.** `Deliveries!B6` says `2 + 0.25 per block`; actual `delFee` (`index.html:1801`) is `(2 + 0.25 × min(14, distance)) × route-planner multiplier × rating multiplier`. Thus additional blocks beyond 14 do not increase the base fee. Streaks, scanners, early/late adjustment, rounding and a one-credit floor are applied in `deliverJob` (`1803–1809`). The workbook's 8-block example is arithmetically correct, but not a general full-payout calculator.
6. **Construction exists in code, while the design/plan are historical specifications.** Current code has persistent `save.constr` and `save.simClock`, 5–25 simulated-minute cost-scaled timers, queued warehouse options, pending-town placeholders, and deferred completion. It follows the plan's correction of the design's clock proposal. All plan checkboxes are still unchecked, so checkbox status must not be used as implementation status.

## Construction design, plan and current-code reconciliation

- Design:128 lines. Objectives: visible timed building, unavailable until completion, concurrent short builds, game-clock dependence and persistence. Non-goals: weather/audio realism, fuel/traffic ETA/fatigue economics, warehouse cancel/refund, timed roads. Queue entries include kind/site/key/position/cost/start/duration/meta. Warehouse purchases reserve their option. Town buildings use a temporary non-earning/non-delivery `constr` tile. Completion applies the original effect, refreshes geometry and saves. Town undo cancels pending entry/refunds. Suggested tests cover progress clamps, exactly-once completion and undo refund.
- Plan:567 lines, five tasks: persistence; shared queue/tick/completion and scaffold sync; warehouse purchase/panel flow; town purchase/render/undo flow; self-check and manual browser verification. Source line numbers are pre-change references, not current anchors. Commands name a developer-local Windows-drive path and are instructions for historical implementation work, not audit requirements or execution evidence.
- **Clock correction is deliberate and implemented.** Design:21–23 and 51–54 propose `sim.sec`; plan:7–11 explains this resets during site load and substitutes `save.simClock`. Current defaults/load at `867–879`, helpers `887–893`, and tick `3915–3921` implement the persistent accumulator. Its units are simulated minutes despite the `sim.sec` legacy name. Hidden tabs set elapsed dt to zero (`3916`).
- **Visual detail differs from the design.** Design:67–70 requests wireframe/radial progress-ring scaffold. Current `900–906` creates a scaled amber box, and `939–944` grows it; no ring in that path. Town construction renders a small amber riser and posts. This conclusion is from source only, not a visual run.
- **Warehouse availability may wait beyond the timer.** Design:103–108 calls for refresh on completion, including non-active lite sites. Current `909–937` writes ownership immediately, but active-shift layout reload is suppressed and the user is explicitly told “Ready after this shift.” Non-active warehouse completion contains no lite-site rebuild branch. Full consequences for lite geometry are left to the main code audit.
- **Roads/land/Unit 7 remain immediate.** Actual `applyTool` handles land/Unit 7 purchase immediately (`3042–3052`), roads immediately (`3066–3067`), and queues other building tools (`3068–3072`). This matches the detailed road exception, but the design/plan's opening phrase “every purchase” is broader than actual scope.
- **Undo promise is not enforced at completion.** Design:115–119 says once completed only bulldoze reverses a build. Current `completeConstr` does not clear `townUndo`; `undoTown` (`3081–3088`) unconditionally restores its snapshot/refunds whether or not it finds a queued entry. Static implication: if the most recent town build completes without another town operation replacing the snapshot, it remains fully undoable. This is a source-derived behavior, not a reproduced browser test.
- **The self-check is narrow.** Current `constrSelfCheck` (`947–960`) checks cost duration clamps and progress at 0/1/overrun only. It does not test negative progress, exactly-once completion, town refund/undo, site switching, saving/reloading or UI flows proposed by the spec. Its presence does not prove it passed; neither it nor plan browser commands were run in this audit.
- **Plan verification has contradictions.** Plan's Task 1 says an undefined function will make syntax checking fail, then immediately correctly says undefined references are not syntax errors. Plan's build verification expects live progress while Build mode pauses the simulation (`index.html:2962`) unless resumed/exited. Plan's town undo example calls the restored plot “for-sale,” although a queued building required player-owned land and undo restores that ownership. These are documentation/test-instruction issues, not executed failures.
