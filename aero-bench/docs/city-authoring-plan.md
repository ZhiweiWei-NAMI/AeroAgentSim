# City Scenario Workbench: Five-Stage Delivery Plan

## Objectives and Boundaries

The workbench lets users select a region from registered OSM sources, then configure airspace, facilities, fleets, orders, and algorithms. Region preview establishes static scene construction only; vehicles, pedestrians, UAVs, order execution, and signal phases require declared actual Providers or sealed evidence.

Formal runs follow `strict specs → immutable ResolvedRun → capability/feasibility preflight → explicit executor → provider barrier → sealed artifacts → independent verifier → public trace viewer`. Select `docker_reference` and `kubernetes_cluster` separately; missing cluster prerequisites do not cause an automatic switch to Docker. An authoring build job ID is not a formal Run ID.

Current status (2026-09-30): **Stage 1 has not passed**. Joint acceptance of the new 414 buildings, ground source data/SUMO, street facilities, weather, and rendering remains incomplete; earlier static/configuration/local-planning evidence covers its original jobs only. Subsequent actual Provider runs remain blocked; physical logistics actions do not start first. This document retains 2026-09-28/29 records; the most recent status table governs current gates.

## Stage 1 Execution Path

The selection static-publication path below is implemented. The new 414-building render path still needs the same facility/roof geometry and effective ground inputs; earlier selection acceptance does not establish acceptance of the new city.

`SceneSelection` contains `source_id`, raw OSM SHA, five WGS84 origin vertical/horizontal parameters, and metric ENU bounds. Browser selection uses WGS84→ECEF→ENU; the compiler emits separate `effective.osm.json` for OSM2World and `sumo-network.osm` for SUMO. Name the three source digests `raw_source_sha256`, `effective_osm_sha256`, and `sumo_source_osm_sha256` respectively; they are not interchangeable.

The official OSM2World builder generates the mesh pack. A digest-pinned SUMO container builds the network using the compiler's declared aeqd projection; the existing city pipeline derives roadbeds, sidewalks, lanes, crossings, markings, lamps, and actual signal positions from that network and the same-job pack. The building finalizer checks clearance against the displayed final roadbed/walkbed and generates BigCity placements from same-job pack footprints; hidden roads in the original pack do not incorrectly remove buildings. Static signals show no fabricated phases.

The static bundle manifest binds the selection, all three sources, compiler, pack, network, roads, building placements, signals, visual assets, and style/BigCity tree digests exactly. The full BigCity tree and road/lamp assets are sealed by file SHA/size; browsers validate content-addressed bytes before assembly. Network XML, netconvert commands, and logs remain in private evidence; HTTP exposes `ready`-job manifests and declared assets only. Publication uses private staging and atomic no-replace; any verification failure prevents `ready` publication.

The first registered source, `shanghai-central-osm-v1`, spans latitude 31.2228–31.2371 and longitude 121.4636–121.4868, with a source-file size of 4,868,022 bytes and SHA-256 `d0f3f30f846e8145aecd497e20ee95bc58e5cb0b3d4b4f46d1339e285217b847`. The separate `shanghai-jingan-osm-v1` source is a small Jing'an snapshot from [OpenStreetMap API 0.6](https://wiki.openstreetmap.org/wiki/Api06); provenance, supplemented complete ways, normalized digests, and removed incomplete non-geometric relations are in `validation/city-authoring-stage1-20260928/jingan-source/`. © OpenStreetMap contributors. Both sources, origins, SHAs, and paths are registered in `aero_bench/authoring/sources.json`; changing a source requires a pinned digest and authoring-service restart, or another registry via `--sources-manifest`. The official API's JSON root version string and relations beyond the bounds can be processed with `python -m aero_bench.authoring.source_import --input RAW.json --supplement FULL-WAY.json --output SOURCE.osm.json --report REPORT.json`; missing building or traffic-restriction members fail explicitly.

Selection scenes have independent drafts saved only after publication and browser assembly are ready, binding raw source, exact selection, job, pack, and presentation digests; refresh revalidates and reloads the same job. They do not write old-city drafts. The configuration protocol bound to selection identity began as `city-selected-scenario/v2`; current facility extensions use `/v3` and record facilities, no-fly time windows/provenance, airframes/payloads, batteries, and background flow. The selection interface is integrated and airframes checked against 24 local display models; formal execution is not integrated. Static previews contain no vehicle/pedestrian trajectories, UAV flight, order execution, or signal phases.

The selection road generator derives asphalt, sidewalk paving, markings, crossings, and lamp positions from SUMO lanes, junctions, and pedestrian topology; the browser assembles sealed textures. GPU browser acceptance of job `1532a422347d1d24dd88f92dc020c0a95e91520e251b4950755f851cd3fac191` shows 727 lanes and 124 lamps. Sidewalks use supplied paving textures; although `Marble001` exists in the catalog, the selection does not automatically apply marble to the ground. Unclassified ground stays neutral; new marble areas need verifiable plaza/pedestrian polygons, corresponding material classification, and coverage acceptance.
