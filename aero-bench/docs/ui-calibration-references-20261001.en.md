# UI calibration reference study

Date: 2026-10-01  
Scope: operational layout, linked map and video interaction, exception presentation, and object context for the additional AERO-BENCH frontend refinement

The findings below come from visually inspecting the source screenshots at their downloaded resolution and then checking the corresponding interaction documentation. The two contact sheets are indexes; the original images remain in the evidence directory for closer review.

## Resulting spatial and interaction language

The flight references support two connected states with the same underlying selection and clock:

1. **Operations overview.** The 3D city remains the dominant surface. A compact run header, collapsible fleet and task rail, contextual detail panel, persistent minimap, and prioritized event strip occupy the edges. A selected aircraft may expose one camera preview.
2. **Aircraft inspection.** The selected onboard sensor becomes the main image. The minimap, aircraft identity, task or order, source label, freshness, compact telemetry, and current event remain visible. One exchange action returns the observation scene to the main position without resetting state.

Selection should travel through this chain: fleet row, scene object, minimap marker, event, detail panel, and camera source. Each surface should resolve the same object identifier and simulation timestamp. An event click may change selection and observation location. It should not send a vehicle command.

The minimap should use a simplified 2D representation with north, scale, facilities, routes, restrictions, event locations, and decluttered moving assets. Aircraft heading and camera or gimbal direction need different marks. When observation-camera bounds can be represented honestly, show a viewport indicator that can be dragged after a movement threshold. Completing that drag should suppress the following click. In onboard mode, a navigation gesture should visibly switch to free inspection and retain a **Return to aircraft** action.

Video status belongs inside the camera surface. Use labels such as **Simulated RGB**, **Live video**, **Recorded video**, **Loading**, **Stale**, **Disconnected**, or **Sensor unavailable**. The status should carry the frame timestamp and source identifier when the provider supplies them. A last frame may remain visible only with a stale or disconnected treatment that cannot be mistaken for current imagery.

## What to leave out

- FlightHub's hardware-specific camera, gimbal, AI, dock, and emergency controls unless an AERO-BENCH provider exposes the exact capability.
- QGroundControl and Mission Planner map gestures that issue flight commands.
- A default multi-video wall, ornamental gauges, and rows of KPI cards.
- AVEVA and XHQ business metrics without a direct link to the active mission, order, facility, vehicle, or event.
- A green-equals-good status system. Labels and symbols should identify activity, connection freshness, and health independently.

## Review evidence for the next increment

The first end-to-end review should start from a visible exception in overview, select the affected aircraft, promote its camera, locate the incident on the minimap, inspect mission and facility context, then return to overview. Selection, event focus, simulation time, and task context should survive every transition. The browser network or command trace should show that observation clicks, minimap drags, and view exchange emit no flight or gimbal commands.
