# P1: runnable platform slice on aerokernel

Implemented and checked on 2026-10-08, Python 3.11.12. The platform requires the
additive M2 relation and sampled-frame APIs in the concurrently developed local
`../aerokernel` checkout. No kernel, AeroGraph, AeroBench or legacy module was
edited. The legacy `aeroagentsim.core` imports SimPy, so the new import-light
core lives in `aeroagentsim.platform`.

## Run it

The supplied platform virtual environment already has aerokernel installed
editable. Install the platform with its optional server dependencies, build
the frontend, and run:

```sh
uv pip install --python .venv/bin/python -e '.[server]'
.venv/bin/aeroagentsim run scenarios/p1-slice.yaml --out runs/
.venv/bin/aeroagentsim replay runs/<printed-run-directory-name>
.venv/bin/aeroagentsim run scenarios/p1-scale.yaml --out runs/
cd frontend
npm run build
cd ..
.venv/bin/aeroagentsim serve --out runs/ --scenario-root . --frontend frontend/dist
```

Open `http://127.0.0.1:8002/runs`. Start an authored scenario by path or JSON
mapping, list runs, select live or replay, seek journal commits, inspect arbitrary
entities, and request pause/resume/stop. During Vite development on port 3000
the Runs page uses port 8002; `?api=<encoded-origin>` selects another service.
Model assets are optional. These two scenarios explicitly select markers, so
no AeroBench GLB or license dependency was introduced.

Default Python dependencies are aerokernel and PyYAML. `server` adds FastAPI and
uvicorn; `legacy` retains the old simulation stack. Platform imports never
load legacy Environment, Agent, Component, Task, Workflow, managers, data
providers or visualization services.

## Scenario and plugin interface

`scenario.load_scenario(path_or_mapping)` reads `aeroagentsim.scenario/v1`.
Duplicate YAML keys, nonfinite values, absent bindings, incompatible field
schemas, unknown plugins/types, invalid clocks/frames and conflicting writers
are surfaced with configuration paths. Authored initial facts are validated
against registry schemas. Missing observations never become zero or false.

| Section | Authored content |
| --- | --- |
| `registry` | Exactly one `snapshot` + matching `digest`, or `compile` with AeroGraph root, selected types/fields/relations and compiler policy; explicit local type/field/message/relation capabilities |
| `entities` | Arbitrary registered `type`, unique `id`, typed initial `facts` |
| `bindings` | Field writer `rules` or `exact` bindings, lifecycle controllers, optional initial commands/cohorts, separate relation writers and cardinality obligation controllers, pinned sample contexts |
| `engines` | Partition IDs mapping to `plugin` and explicit `config` |
| `presentation` | Pinned viewer-feed type/position/orientation/frame/visual bindings; nonspatial types need none |
| `run` | Explicit `seed`, integer `until_ns`, `advance_ns`, `pacing` (`fast` or `realtime`) |
| `outputs` | Kernel WAL `durability` (`buffered` or `fsync`) |

`Simulation` binds the compiled registry, manifest and engines, then exposes
start/run_until/close and the owned kernel for typed submit/cancel/read access.
`RunSession` owns artifacts, status, fixed host advances and cleanup. There is
no platform state ledger or second scheduler. Viewer reads never invoke engines
or add journal entries.

An installed distribution registers a callable factory through
`aeroagentsim.engines` entry points. A factory receives `EngineBuild` (partition
ID, configuration, registry, manifest, initial entities/facts and declarations)
and returns a kernel `Engine`. Built-ins are resolved lazily. Core does not
inspect domain names or choose timing modes. A P2 adapter can return lockstep
partitions and use kernel RPC without changing the catalog or viewer.

## Engines and research meaning

`kinematic` owns only scenario-selected position, velocity and energy fields.
The scenario explicitly declares ENU metres and a transform revision. A
`move_to` command from rest follows an analytic triangular/trapezoidal trajectory,
bounded by configured speed and acceleration. Busy/non-rest moves are rejected;
`hold` and `stop` brake the actual current velocity. Acceptance, execution,
feedback and terminal receipts come from actual integration. An interrupted
move fails; it cannot also succeed. An insufficient-energy route is rejected
before starting. The explicit point-mass approximation has no collision, lift,
wind or vehicle-specific flight dynamics.

The declared energy model is
`remaining_J -= idle_W * elapsed_seconds + per_m_J * integrated_distance_metres`.
Capacity and both coefficients are scenario parameters. No observation replaces
an absent energy input. Uncommanded initial velocity is integrated physically;
insufficient energy during coasting is an execution fault.

`workflow` runs typed declarative DES machines. State definitions have `on_enter`
actions and transitions triggered by typed events, actual child-command receipts,
owned timers or selected-field `eq/gte/lte` predicates. Actions submit commands,
write owned fields, create/remove controlled entities and emit events. Timers
carry state revisions; stale timers cannot advance a newer state. Dynamic
creation and fact publication use separate committed waves, preserving kernel
writer binding rules. Lifecycle removal remains subject to the kernel's native
cleanup and incident-relation rules.

`records` captures a committed source fact, payload and source acquisition stamp
on a configured typed trigger. A kernel timer holds it until C+20 ms. Only then
does its controller create the concrete record; the next committed writer wave
publishes acquisition, availability, subject reference and measured sample,
asserts the actual observation-subject edge, and activates its directional
minimum obligation. Acquisition and availability use separate explicit canonical
clock records. The record and edge cannot exist before release.

`threshold` supports a deliberately narrow, authored expanded-AST profile:
`gte(subject.position[index], parameter)` with `entered` transition semantics.
The manifest pins role identities, producer, native clock/mapping, upstream cone
and parameters. Evaluation runs at kernel settled sample boundaries, recording
one `SampleFrame` per context/physical time with its permitted cut and causes.
Only a previous **known false** and later **known true** produces a typed event.
Initial true, missing inputs and unknown-to-true produce none; an unknown frame
breaks the baseline. Tests retract a real input to exercise this behavior and
differentially check positive/negative/missing/first-true cases against the
read-only native AeroGraph expanded runtime. Its reference SHA-256 is pinned
in the scenario. This plugin is not a general AeroGraph expression interpreter.

`p1-slice.yaml` compiles actual `oo:UAV`, `oo:Order`, `oo:MetricObservation`,
selected native fields and `oo:relation:observation-subject`. Its explicitly
authored concrete `aas:KinematicObservation` inherits the actual MetricObservation
and ObservationRecord chain. The compiler retains source assertions/provenance;
the local capability and threshold contract remain proposed research content.
The source declares a 1:1 subject per record; its missing inverse direction is
explicitly authored as unconstrained many records per subject in the scenario.

Five spatial entities fulfil ten orders in two waves. The operations workflow
issues moves and waits after physical arrival. An independent DES reviewer
waits 100 ms and emits `aas.business.accepted`; only that separate business
input completes an order. Removing the reviewer leaves all orders awaiting
acceptance. This is a local acceptance capability, not a claim that the complete
native Order fulfilment contract is implemented. The operations return lag is
10 ms; no implicit physical/business completion or sampled feedback is added.

## Storage, HTTP and replay

Each run contains `journal.jsonl` (kernel WAL), `index.json` (complete-record
byte offsets), `manifest.json`, the source `scenario.yaml`, canonical
`scenario.json`, compiled `registry.snapshot.json` and `runtime.registry.json`
(including explicit local extensions). The manifest pins source registry and
full scenario digests. The execution owner alone updates the small index.
Incomplete trailing writes never become feed commits. Faults retain their valid
prefix and report the actual error; service restart marks unfinished runs
interrupted and offers replay without pretending to resume execution.

The Python projector maps committed facts, lifetimes, retractions, real edge
changes, typed messages and action receipts to the pinned TS contract. All
kernel journal indices, including empty intent/control/seal records, remain
contiguous; feed index 1 follows the header. Nanoseconds stay decimal strings.

| Endpoint | Behavior |
| --- | --- |
| `POST /v1/runs` | JSON scenario mapping, `{scenario: mapping}`, or `{scenario_path: path}`; validate then start a worker |
| `GET /v1/runs` | List real run manifests/status |
| `GET /v1/runs/{id}/header` | Registry/type/field/frame/presentation RunHeader |
| `GET /v1/runs/{id}/commits?from=1&limit=256` | Read complete indexed commits, next cursor and status |
| `GET /v1/runs/{id}/stream?from=1` | SSE live tail; Last-Event-ID resume; explicit terminal end event |
| `POST /v1/runs/{id}/{pause,resume,stop}` | Request worker control; pause takes effect at a sealed advance boundary |

The local service uses one Linux fork worker per run, preserving its immutable
compiled inputs without re-reading AeroGraph. FastAPI stays responsive while
the worker owns execution. Scenario file paths are scoped to the configured
root. Pacing uses wall time only to delay explicit simulation advances.

`feeds/http.ts` implements paged replay and incremental SSE, including fragmented
CRLF/multiline messages, duplicate resume delivery, lossless time checks and
cursor-gap errors. A bounded reconnect retries only the read transport; it
does not retry simulation actions. Errors remain visible with the last real
recorded state. RunsPage reuses ViewportView, FeedStore, PlaybackClock and
EntityInspector unchanged. The current inspector correlates messages by
entity ID, whereas kernel sources/targets are partition IDs; entity command
receipt filtering is a viewport follow-up, not a fabricated association in P1.

acceptances. The CLI reports end-to-end wall time (including compile, bootstrap,

## Kernel issues

1. **Relation decoder registration:** `codec._record_classes` imports
   `aerokernel.relations` but omits it from the enumerated module tuple. A
   manifest with RelationRule/ObligationRule therefore fails cloning/replay with
   `RECORD_TYPE: unsupported record`. `platform/kernel_compat.py` registers only
   the actual kernel dataclasses into its existing closed decoder table, rejects
   name collisions, and changes no encoding or semantics. Simulation and CLI
   replay apply this small repair. Remove it when upstream includes relations
   in the table. No kernel source file was modified.
2. **Burst command causality cost:** 1,000 simultaneous bootstrap commands cause
   repeated parsing of large intent/receipt records in kernel
   `storage.RecordTable.__getitem__` via `cause_refs/item_at`. Interrupted
   profiling attempts did not produce a throughput result. The shipped scale
   workload explicitly exercises real initial-velocity integration; it does
   not substitute fake receipts for a command benchmark.
3. Dynamic entities cannot publish their owned facts in the same creation wave.
   Engines explicitly use a following committed writer wave. Event topics equal
   to partition IDs address that partition directly; authored arrival,
   business-acceptance and threshold-events topics avoid unintended self routes.
   These are respected kernel rules, not disabled validations.

Concurrent GLM work used two actual DSH sessions with
`workbuddy/glm-5.3-flash`, max output 131072, no effort setting, and separate
scratch directories/file ownership. The larger attempts stalled and were
interrupted. Smaller reviewed outputs contributed eight invalid-scenario
cases and a complete viewer-contract fixture; platform/frontend tests verified
both before integration. Core semantics and final code remained under the
primary agent's review. Scratch/profile output is excluded from delivery.
