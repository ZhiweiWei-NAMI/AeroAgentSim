## Confirmed bug 1 — `endpoint_pair` identity is reused across edge versions (high)

`validate_relations` (relations.py:638-639) passes only the **latest row per edge ID** to `validate_graph`, but the pair-uniqueness check in relation_sweep.py:20-29 keeps no history, while `RELATION_PAIR` is raised from `identities[pair] != edge.edge_id` regardless of temporal disjointness.

Reproducer (repro7.py, passed `Interval` sanity checks in repro1):

```
owner: initialize  AssertEdge("a", R, S1→T1, [0, ∞))
owner: integrate   CloseEdge("a");  AssertEdge("b", R, S1→T1, [3, ∞))   # one wave, t=3
[endpoint_pair] KernelError: RELATION_PAIR: endpoint pair identity reused
```

The identical script under `identity_policy="edge_id"` succeeds, and a different pair (`T1→T2`) succeeds under `endpoint_pair`. So the canonical same-wave *replace* pattern that `test_replace_reads_two_knowledge_prefixes_and_sdk_sources` establishes for `edge_id` (test_m2_relations.py:140) is impossible for a same-pair rewrite under `endpoint_pair`, even though the two versions are temporally disjoint (`[0,3)` vs `[3,∞)`) and `pairs` (sweep line 44) would never hold both at once. The sweep checks pair identity across versions of an entity's lifetime instead of per effective graph. Note the kernel's own `CloseEdge`+re-assert at *later* waves also fails (repro8 case: `[0,4)` then `[4,∞)` → rejected), so reuse after an arbitrarily long gap is permanently poisoned.

## Confirmed bug 2 — `validate_graph` sees only effective rows, but counts endpoints from them (medium-high)

relation_sweep.py:50-63 adds `counts[scope] += sign` only for rows with `valid is not None`, and cancel/terminate versions are `None`-valid and filtered by relations.py:587-594 (`state.edges[e][-1]`). Consequences, both verified:

1. **Orphaned final version escapes maximum** (repro8): history `a=[0,5), b=[5,∞), a=[5,∞)` (pair overlap in time) — final rows are `{b, a'}`; since `a'` starts when `a` ends, no two final rows overlap and `RELATION_MAXIMUM` never fires at 5. The directional maximum is only checked against final rows, so an overlapping pair whose older version is superseded in the same wave is silently accepted.
2. **Minimum cannot be satisfied by a row that terminated before the endpoint's removal instant.** In `validate_relations` the sweep runs on the post-mutation graph while lifetime closure is validated against `candidate.instant` (relations.py:607-637); a final terminated row contributes nothing, which is consistent, but the *max* asymmetry in (1) shows the effective/final confusion is directional.

## Directional suspicion — dependency scope and read-side lag are one-sided (unconfirmed end-to-end)

`scoped()` (relations.py:530-542) filters only `source.id`/`source.type_id`; targets are never filtered, and `notify_relation` computes eligibility from `dependency.lag_ns` (547-553) while the reference reader reconstructs its read instant as `view.instant.ns - reader_lag` (test_m2_relations.py:108-109). My probes (repro1 B1-B4, repro4 §3) confirmed `value_only` suppression is pair-set-based (a same-pair replace emits no `changed` notification — by design), but I could not construct a failing scenario where the reader's `available`-based read side disagrees with the writer's lag-shifted notify side within the notified `payload`. Flagging because `available` (set to `candidate.instant` at relations.py:302, 357, 416, 472) is never consulted in `scoped()`/eligibility, so an edge asserted with a future `valid.start` in wave *k* is notified at wave *k* but the reader's lag-shifted read may land inside the not-yet-valid window — the notification ordering is writer-lag symmetric but not validity-aware.
